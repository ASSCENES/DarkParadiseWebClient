# Seeker для Dark Paradise

Клиент использует нативный протокол DreamSeeker: шлюз Node.js разбирает сообщения
Dream Daemon, а браузер рисует карту и открывает игровые интерфейсы.

## Вход

- «Играть как гость» создаёт отдельный гостевой ключ для этого браузера.
- «Войти через BYOND» открывает настоящее окно secure.byond.com. После входа
  DreamDaemon проверяет выданный BYOND сертификат через Hub, и сайт сохраняет
  подтверждённый ckey. Пароли BYOND сайт не принимает.
- Сессия сохраняется на 30 дней. «Аккаунт / сменить вход» позволяет выйти;
  выход сразу закрывает связанные игровые соединения.
- Подтверждённый BYOND-вход использует существующий `account_ckey`: персонажи,
  настройки, права, наигранное время и баны относятся к этому аккаунту.
  Гостевой вход не даёт доступа к данным BYOND-аккаунта.

Используется штатная CGI-аутентификация BYOND, а не OAuth. Отдельный маленький
`byond-auth.dme` запускается в CGI/ultrasafe-режиме без игрового мира и порта.
Нужна доступность BYOND Hub. Если сертификат не подтверждён, вход отклоняется.

Исходники веб-клиента изменяются в существующем `Desktop/Seeker/seeker`;
в Paradise находятся только DM-интеграция и `tools/seeker-auth/native-auth.c`.

## Сервер

Нужны Node.js 22+, gcc с 32-битными заголовками, OpenSSL 3 x86 и **Linux x86 BYOND 516.1682**, ELF build ID
`e9cdd7c77f6ceac5c3ac42b6f5574f388a969bde`.

```sh
npm ci --omit=dev
DreamMaker byond-auth.dme
gcc -m32 -shared -fPIC -O2 -Wall -Wextra -Werror \
  -o /srv/paradise/libseekerauth.so native-auth.c -ldl
```

Адаптер меняет одну точку обработки сетевых сообщений в памяти движка.
Это не официальный API BYOND. Перед установкой он проверяет архитектуру,
ELF build ID и начало функции. Для других сборок нужны отдельные изменения
и проверки; переносить адреса функций на другую версию нельзя.
Обычные подключения DreamSeeker передаются исходному обработчику.

В конфигурации Paradise:

```text
SEEKER_AUTH_SOCKET data/seeker-auth/verify.sock
LAUNCHER_REQUIRED
```

`GUEST_BAN` должен быть выключен, чтобы разрешить гостевую игру.
После изменения DM-кода нужны компиляция и штатный перезапуск игрового мира.

Каталог сокета должен быть доступен пользователю службы Seeker на запись,
а Dream Daemon — на подключение. Сокет имеет права 0600. Если игра работает
в контейнере, монтируется весь каталог, а не отдельный сокет.

```sh
SEEKER_ORIGIN=https://spacestation13new.ru \
SEEKER_AUTH_SOCKET=/srv/paradise/data/seeker-auth/verify.sock \
SEEKER_AUTH_STATE=/var/lib/seeker/sessions.json \
SEEKER_BYOND_RUNTIME=/opt/seeker-byond \
node server.js --dd PUBLIC_GAME_IP:7777 --port 8095 \
  --cache /var/lib/seeker/cache --rsc /srv/paradise/paradise.rsc
```

`SEEKER_ORIGIN` включает авторизацию и требует фиксированный `--dd`.
Служба слушает только 127.0.0.1; nginx должен перезаписывать `X-Real-IP`
значением `$remote_addr` **и для HTTP, и для WebSocket**. `www` нужно
перенаправлять на домен из `SEEKER_ORIGIN`. Не публикуйте порт Node.js напрямую.
`SEEKER_BIND` предназначен для явного изменения адреса прослушивания.

`SEEKER_BYOND_RUNTIME` содержит официальный DreamDaemon, libbyond/libext,
32-битный ld-linux.so.2 и его системные зависимости. На текущем хостинге
используется отдельная копия установленного BYOND с библиотеками его контейнера;
игровой процесс и Docker для проверки входа не требуются. Каталог принадлежит
root и недоступен службе на запись. Скомпилированный byond-auth.dmb лежит рядом
с byond-auth.js. Одновременно запускается не более четырёх проверок, каждая
ограничена 12 секундами. Исходники обработчика не подключаются к paradise.dme.

Для `/auth/byond/callback` в nginx отключается access_log: сертификат приходит
в строке запроса. Не включайте журналирование её содержимого. Ответ сразу
перенаправляет на чистый URL с no-store и Referrer-Policy: no-referrer.
Отдельная HttpOnly/Secure/SameSite=Lax cookie связывает возврат BYOND с браузером,
а одноразовый state ограничивает его конкретным запросом входа на 10 минут.
Основная cookie сессии сохраняет SameSite=Strict.

Без `SEEKER_ORIGIN` доступен прежний режим разработки без авторизации,
с общим гостевым ключом. Не используйте его для публичной игры.

Состояние сессий содержит хеши случайных cookie и подтверждённые аккаунты,
сохраняется атомарно с правами 0600. Потеря файла завершит сохранённые входы.
Не редактируйте его при работающей службе.

## Развёртывание PR

На хостинге уже настроены служба Seeker, закрытый сокет и
`SEEKER_AUTH_SOCKET data/seeker-auth/verify.sock` в игровой конфигурации.
Код игрового сервера не менялся. После установки PR TGS соберёт адаптер
через `tools/tgs_scripts/PreCompile.sh` при `SEEKER_BUILD_AUTH=1`; для этого нужен `gcc -m32`.
На текущем хостинге компилятор, заголовки и OpenSSL 3 x86 уже есть.
Флаг сборки настраивается во внешнем TGS PreCompile-хуке. Другие хосты
без этого флага не получают новую обязательную зависимость от gcc.
Если библиотека отсутствует или несовместима, Seeker остаётся выключен,
а обычная загрузка игрового мира продолжается.

После штатного запуска нового игрового билда сайт увидит ответ
`seeker_auth=1` и разрешит игровые подключения в течение 15 секунд.
Пока игровой билд старый, доступны подтверждение BYOND и сохранение
гостевой сессии; страница честно сообщает об ожидании обновления сервера.
Перезапускать Seeker после PR не требуется.

## Граница доверия

Перед каждым подключением шлюз выдаёт билет `seeker-v2` на 15 секунд.
Билет подписывается HMAC-SHA256. Адаптер проверяет подпись через OpenSSL
до обращения к Unix-сокету: поддельный билет не запускает блокирующий ввод-вывод.
Ключ `ticket.key` (32 случайных байта, 0600) создаётся службой рядом с сокетом;
его нужно сохранять при обновлениях. Ротация ключа требует штатного перезапуска
игры и Seeker с одним и тем же ключом. Одноразовое подтверждение конкретного
входа дополнительно связывает нативного клиента с записью в адаптере.

Dream Daemon
погашает его один раз через закрытый Unix-сокет. Браузер не выбирает
игровой аккаунт, гостевой ключ или IP в билете. Адаптер проводит исходное
нативное рукопожатие, задаёт отдельные ключ и виртуальный CID браузера,
затем восстанавливает реальный IP, полученный от nginx.

До загрузки настроек и выдачи прав Paradise забирает проверенную личность
из адаптера и повторно выполняет `world.IsBanned` с аккаунтом и реальным IP.
Подключения Seeker не получают localhost-права. CID идентифицирует сессию
браузера, не физический компьютер; очистка cookie создаёт новый гостевой ключ.

Cookie: HttpOnly, Secure, SameSite=Strict. Изменение входа требует POST JSON
с точным Origin. WebSocket проверяет cookie и Origin; `/a/<sid>/` проверяет
владельца сессии. Случайный SID сам по себе не даёт доступа к чужому Topic.
Отладочные `/__dump` и `/__snap` должны быть закрыты в nginx.

## Проверки

```sh
npm test
```

Проверяются изоляция гостей, сохранение cookie, подтверждение сертификата,
привязка к браузеру, истечение и повторное использование state и билетов, выход, CSRF,
ограничение попыток и доверие к IP только от локального nginx.

Для нативной проверки создаётся **отдельный** мир:

```sh
mkdir -p /tmp/seeker-test
node native-smoke.js --fixture /tmp/seeker-test/probe.dme
cp libseekerauth.so /tmp/seeker-test/
cd /tmp/seeker-test
DreamMaker probe.dme
DreamDaemon probe.dmb 45009 -trusted -logself
```

В другом терминале, из каталога Seeker:

```sh
SEEKER_SMOKE_DD=127.0.0.1:45009 \
SEEKER_SMOKE_SOCKET=/tmp/seeker-test/verify.sock node native-smoke.js
```

Проверка держит двух гостей одновременно, проверяет разные CID, реальный IP,
подтверждённый аккаунт и отклонение повторного/поддельного билета и бана.
Тестовый мир принимает только тестовые билеты. Не запускайте проверку против
рабочего игрового мира.

## Отладочный режим (только для админов шлюза)

Игроки не видят кнопку «☀ свет» (выключение освещения — по сути fullbright), админам шлюза она доступна.

Шлюз стоит за nginx, поэтому все подключения считаются внешними: войти в режим можно только с токеном
`SEEKER_ADMIN_TOKEN` (drop-in `seeker.service.d/auth.conf`). Админ открывает страницу один раз как
`https://spacestation13new.ru/?admin=<токен>`: токен запоминается в браузере и сразу убирается из адресной
строки. `?admin=` с пустым значением его забывает.
