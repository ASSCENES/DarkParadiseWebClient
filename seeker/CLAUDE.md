# Seeker — заметки для Claude

Браузерный клиент BYOND. Цель — играть в SS13 (сборка ss1984, форк Paradise) в браузере максимально похоже на
DreamSeeker. Пользователь общается по-русски; отвечай по-русски, коротко и по делу. Пользовательская
документация — `README.md`, этот файл — для того, кто продолжает разработку.

## Как устроено

- `server.js` — шлюз на Node (зависимость только `ws`). Подключается к Dream Daemon **нативным протоколом
  DreamSeeker** (`proto/byond-conn.js`: рукопожатие, шифр `proto/crypt.js`), входит гостем (`GUEST_LOGIN`), разбирает
  сообщения сервера и шлёт странице JSON по WebSocket (сообщения одного чтения сокета — одним массивом).
  Отдаёт статику `public/`, ресурсы (`/res/<id>`, `/icon/<id>.png|json|rgba`), кэширует их в `cache/`.
- `public/client.js` — состояние мира в браузере (`state`: turfs, objs, apps, vis, images, screen, anims…), окна
  browse/tgui, чат, клавиши, звук, диалоги.
- `public/render.js` — отрисовка: сцена рисуется 1:1 в offscreen-canvas `scene` (размер view × 32), затем
  растягивается без сглаживания на страницу (`shown = {x, y, s}`, `canvasPoint` переводит координаты мыши).
  Планы/plane masters (`readPlanes`), plates и фильтры, освещение (`drawLighting`: lighting objects с
  `color_matrix` → `lightTile`, emissive, overlay lighting), maptext/runechat, line of sight (`byondView`, порт
  OpenDream), мышь, drag-and-drop, контекстное меню.
- `proto/` — парсеры: `appearance.js`, `objects.js` (тип 8 и блок мобов в типе 7), `mapstate.js` (окно турфов),
  `animate.js` (тип 240), `rsc.js`/`rsccrypt.js`. Полное описание протокола — `PROTOCOL.md` в архиве
  (в исходной машине: `D:\BYOND\proto\PROTOCOL.md`).
- `launch.js` + `config.json` + `start.bat` — поднимает Dream Daemon (если в конфиге `dmb`) и шлюз, **сам
  перезапускает шлюз, если его процесс убить** — так подхватывается новый код без остановки раунда.
- `font.js` (имя семейства и наличие кириллицы в TTF), `png.js` (декодер PNG в сырой RGBA), `dmi.js`.

## Как запускать и тестировать

- Игра пользователя: `node launch.js config.json` (ss1984: DD на 51984, шлюз на 8080). Чтобы обновить код шлюза —
  убей **только процесс `server.js`** на 8080 (по PID), лаунчер перезапустит. Статику (`public/`) достаточно
  перезагрузить в браузере.
- **Никогда не убивай `dd.exe` по имени** — это уронит раунд пользователя. Тестовые процессы — только по PID/порту.
- Все страницы входят **одним гостевым ключом**: новая вкладка на том же сервере выкидывает предыдущую.
  Не подключайся к игре пользователя, пока он играет, без его ведома.
- Тестовый мир: `webtest/webtest.dme` (в архиве), компиляция `D:\BYOND\bin\dm.exe webtest.dme`, запуск
  `dd.exe webtest.dmb 51985 -trusted`. Шлюз без `--dd` (`node server.js --port 8086`) и страница
  `http://localhost:8086/?server=127.0.0.1:51985`. В мире есть тестовые глаголы (`test_*`) и логирование
  `client/MouseDrop/MouseDrag/MouseDown/Click` и `TopicData` подключения.
- **Внимание:** тестовый мир маленький, у него **16-битные id глаголов**, а у Paradise — 32-битные
  (`map.wideVerbs`). То, что работает на тестовом мире, может ломаться на Paradise (так было с drag-and-drop).

## Инструменты отладки

- **Запись сессии** (кнопка «⏺ запись», только админам шлюза: страница с localhost без прокси-заголовков или
  `?admin=<токен>`, `isAdminPage` в server.js). Файл `seeker-record-*.json`: `server.messages` —
  `[мс, 'in'|'out', тип, hex]` всего обмена с игровым сервером (как SEEKER_DUMP, но по кнопке и с исходящими),
  `page` — `[мс, 'gw'|'page'|'console.error'|…, данные]`, `snapshots` — `renderDump()` каждые 5 с, `mouse`.
  Копия у шлюза в `records/`. Разбирать так же, как дампы: проиграть `messages` через `MapState`/парсеры `proto/`.
- `GET http://127.0.0.1:<порт>/__dump` (только с localhost) — шлюз спрашивает у открытых страниц их состояние
  (`renderDump()` в render.js): камера, eye, моб, z, sight, planes/masters, последние 30 действий мыши
  (`mouseLog`), PNG-снимок сцены (`snapshot`, data URL).
- Переменные окружения шлюза: `SEEKER_DEBUG=1` (лог трафика, winget, глаголы), `SEEKER_DUMP=файл.jsonl`
  (все сообщения сервера в hex), `SEEKER_ERRORS`, `SEEKER_DEBUG_RES`, `SEEKER_SNAP_DIR`,
  `SEEKER_GUEST_TICKETS` (JSON: доп. серверы с билетами).
- `tools/mitm.js <порт> <host:port> [лог]` — расшифровывающий ретранслятор между **настоящим DreamSeeker** и миром:
  пишет все сообщения клиента в открытом виде. Лучший способ узнать точный формат того, что шлёт DreamSeeker
  (`dreamseeker.exe byond://127.0.0.1:<порт>?…`).
- `tools/topic-probe.js`, `tools/dpweb-probe.js` — разовые пробы (параметры подключения; вход в веб-шлюз
  Dark Paradise по билету).
- Встроенный браузер Claude удобен: `renderDump()`, `state`, `planes`, `drawn`, `camera()` доступны в консоли.

## Уроки (то, на чём уже обжигались)

- **Не угадывай смещения в сообщениях, вычисляй их по флагам.** Блок мобов в типе 7 раньше искался перебором
  старта; на шаге без поворота перебор попадал на байт раньше и терял перемещение — моб «стоял», камера уезжала
  за eye. Теперь старт берётся из `sightHeaderEnd()` (флаги заголовка), перебор — только запасной путь.
- **Ширина id глаголов.** Сообщения 2 (клики, MouseDrag/Drop 0x93/0x92, глаголы) пишут id как u16 или u32 по
  `map.wideVerbs`. Ошибка ширины = сервер молча игнорирует сообщение.
- **id внешностей (appearance) переиспользуются сервером.** Не кэшируй вычисления по `a.id`; ключуй по содержимому
  (так исправлен кэш тайлов света `lightTile`).
- **`.maptext` из стиля карты — базовый стиль всего maptext** (и MeasureText). Runechat Paradise меряет голый
  текст через `client.MeasureText` (шлюз спрашивает страницу: сообщение `measure` → `layoutMaptext`), высоту рамки
  берёт ×1.25 и рисует от верха рамки; несовпадение шрифта = текст висит выше головы.
- В строке подключения DreamSeeker (`byond://host:port?topic`) параметры идут в начале сообщения входа 26:
  строка `?a=b`, `\0`, затем остальное (у нас `GUEST_LOGIN` начинается с пустой строки `00`). На странице это поле
  «Параметры подключения» формы сервера: хранится в sessionStorage вкладки, уходит шлюзу как `login=` в URL
  WebSocket (`loginTopic()` в server.js), к нему добавляется билет `dpweb` для серверов из `GUEST_TICKETS`.
- **Окна и экранные координаты.** tgui двигает окно сам: `window.screenLeft/Top` + мышь → `winset pos`. В iframe
  screenLeft — это вкладка, поэтому шим в `patchHtml` подменяет screenLeft/Top/X/Y на настоящее место фрейма
  (`seekerFramePos` → `framePos()` в client.js; начало координат страницы берётся из `screenX - clientX` событий
  мыши) и ставит `devicePixelRatio = 1` (всё в CSS-пикселях). Иначе окно дёргается/прыгает при перетаскивании.
  Окна «свои» (`w.own`) открываются всплывающими (`openPopup`/`hostIn`); закрытый попап теряет страницу — она
  возрождается из `w.html` (tgui сам просит полное обновление по `ready`). Встроенная панель Claude попапы не
  открывает совсем: проверять в Chrome (headless через CDP тоже годится, но позиции окна он зажимает).
- Иконки tgui (`DmIcon`): `icon_ref_map.json` даёт `"[0xc<индекс>]"` — индекс в списке ресурсов мира (сообщение 14,
  `map.resources`); шлюз отдаёт кадр `?state&dir&frame&movement` PNG-ом (`iconFrame` в server.js).
- Параллакс Paradise: слои сдвигаются сразу на 1–3 px за шаг (`pixel_w/z`, их `animate()` к тем же значениям
  ничего не делает), а карта скользит — звёзды дёргались. `parallaxGlide()` в render.js растягивает сдвиг слоя на
  время скольжения своего моба; перескок на 480 px (тайлинг) берётся как есть.
- **Сообщение 241 (изменения турфов) сжато.** Три столбца по n значений (индексы клеток, appearance, area), в каждом
  `u32 0xffffffff, u8 k` = предыдущее значение ещё k+1 раз; затем необязательно `u16 m, m × (u32 area, u32 appearance)`.
  Старый разбор «n × u32 подряд» давал мусорные id — клетки пропадали («дыры», сквозь пол виден параллакс), особенно
  после смены освещения (лазер, выключатель: свет в Paradise — underlay турфа). Проверено проигрыванием дампа.
- Наложение со сдвигом `pixel_w/z` при `transform` родителя: сдвиг добавляется после поворота/масштаба, не крутится
  с ним (`wx/wy` в collect, blitIcon, lightBlit). Так Paradise рисует лучи hitscan (`/obj/effect/projectile/tracer`).
- **Иконки, собранные миром на лету** (`new /icon`, `Blend`, `Turn`… — ушибы Paradise, многие оверлеи) — ресурс
  типа 12 «DDMI»: не картинка, а рецепт (стековая программа над ресурсами мира по их индексу в сообщении 14). Сервер
  шлёт его передачей 159 **с пустым именем** — раньше шлюз такие отклонял. `ddmi.js` собирает из рецепта обычный
  DMI; хранится только в памяти (`builtIcons`), т.к. индексы ресурсов свои у каждого сервера. Формат опкодов — в
  шапке `ddmi.js`, образцы — глагол `test-ddmi` тестового мира.
- `animate()` без цели (продолжение цепочки) приходит **отдельным сообщением 240 с fresh = 0**: шаги добавляются в
  конец играющей цепочки, а с `ANIMATION_PARALLEL` — новой параллельной от её начала. Раньше такие сообщения
  выбрасывались — balloon alert'ы Paradise (поднимаются в одной цепочке, проявляются в другой) были невидимы.
- Тряска экрана (`shake_camera`) — `animate(client, pixel_x/y)`: цель типа 5 в сообщении 240 (ref 0), внешние виды
  с именем "client". Ключ анимации `client`, смещение добавляется к камере в `camera()` (`clientPixels`).
  Простое `client.pixel_x = …` без анимации, похоже, идёт в заголовке сообщения 7 — не разобрано.
- **Обычные PNG как иконки** (заставка лобби Dark Paradise — `icon = new(file.png)`): у них нет описания DMI, и
  `readDmiMeta` раньше не ставил `cols` → координаты кадра NaN, картинка не рисовалась (чёрное лобби).
- Наложения/подложки наследуют `pixel_x/y` своего атома (в `collect` детям передаётся `at.px`, не `px`).
- **Лимит Topic.** Paradise-подобные миры (`SECOND_TOPIC_LIMIT 10`) игнорируют 11-й Topic за секунду и пишут
  «слишком много действий за секунду». При входе statbrowser на каждый из нескольких `init_verbs` шлёт `Send-Tabs`
  по каждой вкладке — десятки сразу. `sess.topic` в server.js — очередь: не больше 8 в секунду, повтор того же,
  что ещё ждёт, выбрасывается. Все Topic (и из окон, и со страницы) идут через неё.
- **Официальный веб-клиент BYOND** (`D:\BYOND\web\webclient.dart.js`, 1.7 МБ, Dart→JS, читаемые имена) — справочник
  по смыслу полей. Протокол у него свой (веб), раскладку байтов переносить нельзя — только смысл, и проверять на
  нативном трафике (дамп + тестовые глаголы). Сборка старая: нет `render_target` и фильтров кроме blur, нет DDMI.
  Его `processMovableChangeMessage` дал заголовок сообщения 7: пары u16 «наш моб, eye» в 0x02/0x04; в 22-байтовом
  блоке первый байт — eye это наш моб (0 → ещё 5 байт: тип + ref атома eye); второй байт флагов: 0x04 sight u32,
  0x08 i16×4, 0x10 `client.pixel_x/y`, 0x20 i16×4, 0x40 8 байт (`readSightHeader` в server.js). Раньше eye
  брался из первого u16 (позиция моба) — слежка призрака/камеры не двигала вид; неизвестные биты уводили в перебор.
  У него же сдвиги наложений (и pixel_w) крутятся вместе с transform родителя — расходится с нашим исправлением
  лучей hitscan; не проверено на настоящем DreamSeeker.
- **Загрузка ресурсов.** (1) Иконки идут по WebSocket страницы (`{t:'icon'}` → бинарный кадр: u32 длина, JSON
  `{id, meta}`, PNG), а не двумя HTTP-запросами: браузер держит ~6 соединений к сайту, и запросы, ждущие ресурс от
  сервера до 20 с, забивали очередь — на новом месте (Лаваленд) спрайты были «квадратами». (2) Пакет `resources`
  помечается в `cache/transfers.txt` как полученный («у меня есть» при следующем входе) только если его просили
  не мы и каждая запись легла в дисковый кэш. Раньше туда попадали пакеты с иконками на лету (тип 12, только в
  памяти) и неопознанными записями — сервер их больше не слал никогда. При обновлении шлюза старый
  `transfers.txt` нужно удалить. (3) Клетка, чья иконка ещё не пришла, рисуется чёрной, а не дырой в космос.
- **screen_loc от верха** (`TOP:-13,…`, `NORTH…`): DreamSeeker совмещает с верхом клетки **верхний** край иконки
  любой высоты, иначе — нижний (сверено с DreamSeeker на лобби Dark Paradise: рамка 151×123 у верхнего края,
  кнопки в 13/40/70 px от верха, телевизор `CENTER:140` — нижним краем). Пиксели можно писать и до клеток:
  `SOUTH:6+1`. maptext понимает `vertical-align: middle/bottom`.
- maptext: `font-size` в px считаем как pt (призраки/LOOC Paradise просят `'MS Serif'` 6px — в DreamSeeker
  читается как обычный runechat); `MS Serif` (растровый шрифт Windows) заменяется шрифтом карты.
- DDMI `Blend(цвет, ICON_ADD/SUBTRACT)` меняет только цвет: прибавка к альфе делала из иконок мобов квадраты.
- Окна: `.win iframe` с `min-height: 0`, иначе iframe не сжимается ниже 150 px и короткие окна (tgui-say 30 px)
  показывают только верх своей страницы. tgui-say ставится над картой и сразу получает фокус в поле ввода.
- Файлы окон (`/a/<sid>/…`) отдаются с кэшем браузера (`asset.<md5>.*` — immutable) и gzip (`sendBody`):
  tgui.bundle.js 2.5 МБ → 0.6 МБ и один раз за сессию. Файл, который сервер назвал, но не прислал, ждём один раз
  (до 20 с); раньше ожидание повторялось 10 раз — запрос висел минутами и держал одно из ~6 соединений браузера.
- **Повторные входы.** Файлы окон, которые являются ресурсами мира, отдаются по адресу `/c/<crc>/<имя>` (302 с
  `/a/<sid>/…`): адрес не зависит от сессии и кэшируется навсегда; относительные ссылки внутри (шрифты из CSS)
  находятся по имени (`assetIdByName`). Иконки — в Cache Storage браузера (`seeker-icons-v1`, только https/
  localhost), собранные из DDMI не кэшируются (`built`). Статика страницы — gzip + ETag. Второй вход: 2 КБ по HTTP.
- Multi-z в Paradise: у каждого уровня свои plane masters (`… #0`, `#1`…); освещение/emissive — только `#0`.
- Плохие правки производительности пользователь замечает сразу («стало только хуже»): меряй (`?fps=1`),
  не вводи очередей декодирования иконок.
