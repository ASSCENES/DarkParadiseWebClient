# Нативный протокол BYOND 516 (DreamSeeker ↔ Dream Daemon)

Восстановлен по захватам трафика (`proxy.js`) и дизассемблированию `byondcore.dll` 516.1688.
Проверен headless-клиентом (`byond-conn.js`, `login-test.js`) на тестовом мире и на ss1984.

## Кадры (TCP)

| Направление | Формат |
|---|---|
| сервер → клиент | `[type u16 BE][len u16 BE][payload]` |
| клиент → сервер, первый пакет | `[type u16 BE][len u16 BE][payload]` |
| клиент → сервер, остальные | `[seq u16 BE][type u16 BE][len u16 BE][payload]` |

## Шифр (`byondcore.dll`: шифрование `0x102B7BE0`, расшифровка `0x102B7B80`)

```
S = 0
для каждого байта p:  c = p + byte(key >>> (S mod 32)) + S ;  S += p     (всё по модулю 256)
в конец дописывается байт S (контрольная сумма)
```

Шифр сбрасывается на каждое сообщение. Ключ одинаков в обе стороны.
Пустые сообщения (len = 0) не шифруются.

## Рукопожатие

Клиент (`0x10039131`), тип 1, открытым текстом, 22 байта:

| Поле | Значение |
|---|---|
| u32 | 516 (версия) |
| u32 | 276 |
| u32 | `R − 0x01140204`, где `R` — случайное ненулевое число |
| u16 LE | `seq0` — начальное значение счётчика |
| u32 | 1688 (сборка) |
| f32 | 3.0 |

Сервер (`0x101BBCB3`), тип 1, зашифрован ключом `R`:

| Поле | Значение |
|---|---|
| u32 | 516 |
| u32 | 490 (минимальная версия) |
| u8 ×3 | флаги |
| u32 … | мусор, пока не встретится `x` с `((x + 0x1BD632F) & 0x4008000) == 0` (этот `x` тоже мусор) |
| u32 | `k`: **сессионный ключ = R + k** |
| u32 … | мусор, пока `((acc + 0xFFDB36E3) & 0x402000) != 0` |

Все последующие сообщения в обе стороны шифруются сессионным ключом.

## Счётчик пакетов клиента (`0x102A5DA0`)

Перед каждым пакетом (кроме приветствия) клиент пишет текущий `seq`, затем:
`seq = (seq * 0x43D4) mod 0xFFF1`, если результат 0, то 1.
(Для протокола < 413 было просто `seq + 1`.)

## Вход (тип 26 от клиента)

Клиент отправляет тип 26 сразу после ответа сервера. Содержимое зависит от пейджера:
- пейджер залогинен — блоб аккаунта (статичный, многоразовый: **это учётные данные, не публиковать**);
- пейджера нет — гостевой блоб, сервер выдаёт `Guest-<число>`.

Общая часть блобов (`7f4556ae…660df1`) похожа на computer ID. Формат гостевой части ещё не разобран:
сейчас все гости из `login-test.js` получают один и тот же `Guest-4037097759`.
Мусорный блоб сервер отклоняет (тип 0, код 6).

После входа DreamSeeker отправляет: 183 (пусто), 11 (`u32`), 13 (`7f 00`), 25 (пусто).

## Инструменты

- `proxy.js <порт> <хост:порт> [папка]` — логирующий прокси, захваты в `captures/`.
- `frames.js <захват>` — разбивка захвата на кадры.
- `crypt.js` — шифр.
- `keysolve.js <захват>` — восстановление ключа по известному тексту (для тестового мира).
- `byond-conn.js` — транспорт клиента (рукопожатие, ключ, счётчик, шифрование).
- `login-test.js <порт> [guest|empty|zero]` — вход и вывод сообщений сервера.
- `re/dis.js` — дизассемблер `byondcore.dll` на `iced-x86`.

## Длинные сообщения (тип 160)

Сообщение длиннее 65535 байт предваряется кадром `[00 A0][00 06][u16 тип][u32 длина]` (открытым текстом, big-endian),
за которым сразу идёт зашифрованное тело указанной длины без собственного заголовка.

## Флаги из ответа на рукопожатие

Третий байт флагов (`p[10]`): бит 0 — id объектов/appearance 32-битные, бит 1 — id вербов 32-битные
(сервер ставит, когда процедур больше 65535, как в ss1984).

## Передача файлов (тип 159)

Заголовок (seq 0): `u32 crc, u32 0xFFFFFFFF, u32 0, u32 2, u8 1, u32 размер, u8 тип, имя\0, "##action=…;…"\0`.
Клиент отвечает тем же типом: `[crc][FFFFFFFF][01]` — файл есть в кэше; `[crc][FFFFFFFF][00][u32 1]` — прислать.
Данные: `[crc][FFFFFFFF][u32 seq][u32 2][u32 смещение][байты]`, seq = 1…n.
Действия: `browse_file;options=window%3dX` и `output_file;window=X` показывают HTML-файл в окне, `load_rsc` кладёт ресурс в кэш.
После действия может идти `u8 1, u32 размер` — тогда данные сжаты gzip, а `размер` в заголовке — до сжатия.

### Ресурсы (ответ на 60)

- Один ресурс — файл под своим именем (`test.dmi`), `crc` передачи равен id ресурса, тип — тип ресурса с флагом `0x80`, если он зашифрован.
- Несколько — файл `resources`: gzip с фрагментом `.rsc` (записи как в файле мира). У зашифрованных записей тип `| 0x80`, а id в заголовке записи скрыт; записи идут в порядке запроса, верный id подтверждается CRC.
- id ресурса — CRC-32 BYOND (`0x102455C0`): старшим битом вперёд, полином `0xAF`, начало `0xFFFFFFFF`.
- Шифр (`0x10260D30`): состояние = id ресурса; для каждого байта `p = c ^ (s & 0xFF)`, затем `s = jenkins(c + s)` (32-битный хеш Боба Дженкинса, `c` — зашифрованный байт). Код — `proto/rsccrypt.js`.

`browse(текст, "file=имя&display=0")` (тип 132 с `file=`) сохраняет файл в кэше клиента, не показывая его.
Страницы окон шлют Topic и через XHR `GET ?…` — DreamSeeker перехватывает такие запросы.
tgui сообщает соответствия имён файлов через `output(…, "…:update")` с `{"type":"asset/mappings","payload":{имя: "asset.<md5>.ext"}}`.

### Фильтры (в appearance, флаг 0x800)

`u8 тип`: 1 blur, 2 outline, 3 drop_shadow, 4 motion_blur, 5 wave, 6 ripple, 7 alpha, 8 displace, 9 color, 10 radial_blur,
11 angular_blur, 12 rays, 13 layer, 14 bloom. Поля идут по битам маски в своём для типа порядке: outline — `f32 size, u32 цвет, …,
u16 flags (0x20)`; drop_shadow — `f32 size, u32 цвет, f32 x, f32 y, f32 offset`; blur — `f32 size`; color — 20 `f32` матрицы.
Цвет — `u32` как у appearance (младший байт — красный). Фильтры plane master-ов SS13 (например, тень «ambient occlusion» на
Game world plate) относятся ко всем плоскостям, передаваемым на эту плиту: передача — экранный объект с именем
`*<имя plane master>: AUTOGENERATED RENDER TGT #n` на плоскости плиты.
